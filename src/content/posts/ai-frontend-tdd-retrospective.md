## TL;DR

- AI가 작성한 프론트엔드 코드를 검증하는 방법을 고민하다 TDD 기반 개발 워크플로우를 도입했다.
- PRD에서 테스트 케이스를 추출하고 Red–Green–Refactor 방식으로 구현했다.
- 하지만 **토큰과 개발 시간이 많이 들었고, 테스트를 거친 결과물에도 요구사항 누락이 있었다.**
- 실제 PR을 살펴보니 일부는 테스트 대상에서 제외된 UI·스타일 문제였고, 일부는 관련 테스트 케이스가 존재했는데도 실제 브라우저에서 문제가 발견된 경우였다.
- 원인은 TDD가 해결하고자 하는 문제와 내가 해결하고자 하는 문제가 달랐기 때문이었다. TDD는 ~를 해결하기 위함이었는데, 그건 ~해야하는 프론트엔드에는 맞지 않았다. 그리고 나는 ~를 해결하고 싶었던 거였는데, TDD는 그걸 일부만 해결해줄 수 있었다. {여기 문장 채워라}
- 그래서 TDD를 중단하고, 원래의 워크플로우로 돌아갔다. PRD 검토·코드 리뷰·실제 화면 QA를 중심으로. 다만, 필요한 곳에 자동화 테스트를 적용하는 방향으로 바꾸려 한다.
- 새로운 워크플로우 구축 후기도 가져올 예정.

**소감: 일단 시도해본 건 잘했다. 너무 냅다 시도해서 좀 돌아왔지만ㅎㅎ**

**교훈: 좋은 방법론을 도입하기 전에, 내가 해결하려는 문제와 그 방법론의 목적이 일치하는지 먼저 확인하는 것 다음에는 놓치지 않기.**

## AI가 만든 코드를 어떻게 믿을 수 있을까?

AI로 개발을 시작하면서 가장 고민했던 건 코드의 신뢰성이었다.

AI에게 기능 구현을 맡기면 코드는 빠르게 만들어진다. 그런데 이 코드가 정말 요구사항대로 동작하는지는 어떻게 확인할 수 있을까?

직접 코드를 전부 읽고 리뷰해야 할까? 그렇다면 AI를 사용해서 절약한 시간을 다시 코드 리뷰에 쓰는 건 아닐까?

그러다 떠오른 것이 **테스트**였다.

테스트 코드가 있으면 AI가 작성한 코드가 올바르게 동작하는지 검증할 수 있을 것 같았다. 그리고 테스트를 알아보다 보니 자연스럽게 TDD(Test-Driven Development)를 접하게 됐다.

사실 나는 테스트 경험이 많지 않았다. TDD에 대해서도 깊이 이해하고 있지는 않았다. 다만 좋은 개발 방법론이라는 이야기를 여러 번 들었고, AI 개발에도 잘 맞을 것 같았다.

그렇게 TDD를 내 AI 개발 워크플로우에 도입했다.

## 내가 만든 TDD 기반 AI 개발 워크플로우

당시 구성한 워크플로우는 다음과 같았다.

1. **PRD 정리:** 구현할 기능과 요구사항을 문서화한다.
2. **테스트 케이스 작성:** PRD를 바탕으로 유닛·컴포넌트·E2E 테스트 목록을 만든다.
3. **TDD 구현:** AI가 테스트를 먼저 작성하고, 테스트를 통과하도록 기능을 구현한다.
4. **최종 검증:** PR 생성 전 E2E 테스트를 수행한다.
5. **PR 생성:** 구현 결과를 정리하고 리뷰한다.

테스트 케이스 목록을 별도 파일로 관리하면서 각 항목의 구현 여부를 확인하도록 했다.

의도는 단순했다. AI가 구현해야 할 내용을 테스트 케이스로 먼저 정의하고, 그 테스트를 모두 통과하면 요구사항을 빠짐없이 구현했다고 판단할 수 있지 않을까?

하지만 실제로 적용해 보니 예상하지 못한 문제가 생겼다.

## TDD를 적용하면서 생긴 네 가지 의문

### 1. 무엇을 테스트해야 하지?

가장 먼저 막힌 건 테스트 범위였다.

프론트엔드에는 검증할 것이 많다. 피그마와 동일하게 화면이 구현됐는지, 버튼을 누르면 올바른 페이지로 이동하는지, API 응답에 따라 적절한 UI가 나타나는지, 예외 상황에서도 정상적으로 동작하는지 등을 확인해야 한다.

그런데 이 모든 것을 테스트 코드로 작성해야 할까?

화면의 여백이나 색상, 이미지 배치까지 테스트해야 할까? 테스트한다면 어떤 방식으로 해야 할까?

당시에는 무엇을 자동화 테스트 대상으로 삼고, 무엇을 직접 확인해야 하는지 판단할 기준이 없었다.

### 2. 테스트 코드는 계속 남겨야 할까?

AI가 작성한 코드를 검증하려고 만든 테스트 코드를 꼭 유지해야 하는지도 의문이었다.

어떤 테스트는 앞으로도 코드 변경으로 인한 회귀를 막아줄 수 있다. 반면 특정 구현이 요구사항을 충족하는지 한 번 확인하기 위한 테스트도 있을 수 있다.

그렇다면 모든 테스트를 계속 관리하는 게 맞을까?

테스트 코드는 작성하는 것으로 끝나지 않는다. 기능이 바뀌면 테스트도 수정해야 하고, 테스트 환경도 유지해야 한다.

AI가 테스트 코드를 빠르게 작성해 준다고 해서 유지보수 비용까지 사라지는 것은 아니었다.

### 3. 꼭 최소한의 구현부터 시작해야 할까?

TDD의 기본 사이클은 Red–Green–Refactor다.

먼저 실패하는 테스트를 작성하고(Red), 테스트를 통과시키는 최소한의 코드를 구현한 다음(Green), 코드를 개선한다(Refactor).

그런데 AI에게 개발을 맡기면 처음부터 상당히 완성도 높은 구현을 만들어 내기도 한다.

이런 상황에서도 반드시 작은 구현 단계를 반복하도록 해야 할까?

물론 작은 단계에는 의미가 있다. 변경 범위를 통제하고, 문제가 생겼을 때 원인을 찾기 쉽게 하며, 설계를 점진적으로 개선할 수 있다.

하지만 모든 프론트엔드 작업을 이 방식으로 진행하는 것이 효율적인지는 별개의 문제였다.

특히 UI·UX 구현에는 테스트 케이스만으로 표현하기 어려운 요구사항이 많았다. 테스트 통과를 중심으로 개발을 진행하다 보니 시각적 구현이나 화면 전체의 완성도를 언제 확인해야 하는지도 애매해졌다.

### 4. AI에게 규칙을 많이 주는 게 정말 좋을까?

TDD를 적용하면서 AI가 따라야 할 규칙과 절차도 늘어났다.

그런데 주변에서는 복잡한 스킬이나 규칙 없이도 AI로 기능을 잘 구현하고 있었다.

내가 너무 많은 제약을 주고 있는 건 아닐까? 이렇게 복잡한 워크플로우가 정말 필요한 걸까?

이건 AI의 성능이 실제로 떨어졌다는 이야기는 아니다. 규칙이 많은 경우와 적은 경우를 비교 실험한 것은 아니기 때문이다.

다만 **규칙을 추가할 때마다 그 규칙이 어떤 문제를 해결하는지 설명할 수 있어야 하지 않을까** 하는 의문이 생겼다.

## 테스트를 통과했는데도 구현이 빠져 있었다

이런 의문을 갖고 있던 중, 실제 구현 결과를 확인하면서 문제가 드러났다.

PRD와 피그마를 바탕으로 테스트 케이스를 작성하고, AI가 TDD 방식으로 기능을 구현했다. 그런데 직접 브라우저에서 화면을 띄워 확인해 보니 요구사항과 다른 부분이 여럿 있었다.

문제는 이 내용들이 나중에 추가된 요구사항이 아니었다는 점이다. **이미 PRD와 피그마 캐시 파일에 정의되어 있던 내용들이었다.**

직접 확인하면서 발견한 문제들을 별도 PR에서 수정했다.

실제 수정 내역은 [GitHub PR #796](https://github.com/PetCampus-Inc/daeng_v2_front/pull/796)에서 확인할 수 있다. 이용권 충전과 예약 설정 관련 커밋을 제외한 나머지는 AI가 초기 구현에서 놓친 부분을 내가 발견해 수정한 내용이다.

수정사항에는 마이페이지와 탭바 스타일, 구성원 화면의 버튼과 빈 상태 이미지, 연결 해제 후 화면 이동, 해제 불가 안내, 일과 화면의 날짜·현황 표시 등이 포함됐다.

여기서 한 가지 궁금증이 생겼다.

**이 문제들은 애초에 테스트 케이스에 없었던 걸까? 아니면 테스트 케이스가 있었는데도 발견하지 못한 걸까?**

### 기존 Test List를 다시 확인해 봤다

기능별 PR에 포함된 `test-list.md`를 살펴보니 두 종류의 사례가 있었다.

첫 번째는 **테스트 대상에서 의도적으로 제외했던 항목**이다.

예를 들어 스타일, 레이아웃, 정적 문구 같은 요소는 별도 테스트를 작성하지 않는다고 명시한 경우가 있었다.

- [구성원 관리 PR #785](https://github.com/PetCampus-Inc/daeng_v2_front/pull/785)
- [보호자 연결 해제 PR #792](https://github.com/PetCampus-Inc/daeng_v2_front/pull/792)

이런 항목을 테스트에서 제외한 판단 자체가 잘못됐다고 보기는 어렵다. 시각적 요소는 일반적인 유닛·컴포넌트 테스트보다 실제 화면 확인이나 시각적 회귀 테스트가 더 적합할 수 있기 때문이다.

문제는 **자동화 테스트에서 제외한 요구사항을 어떤 단계에서 검증할 것인지 충분히 정해두지 않았다는 것**이었다.

두 번째는 **관련 테스트 케이스가 존재했던 항목**이다.

예를 들어 [원장 연결 해제 PR #791](https://github.com/PetCampus-Inc/daeng_v2_front/pull/791)의 Test List에는 연결 해제 성공 후 구성원 목록으로 이동한다는 케이스가 있었다.

그런데 이후 수정 PR에서는 모달을 닫는 과정과 브라우저 히스토리가 상호작용하는 부분을 보완해야 했다.

테스트 목록에 화면 이동이 포함되어 있었다고 해서 실제 브라우저에서 발생하는 모든 이동 문제가 검증된 것은 아니었던 셈이다.

다만 이 사례만으로 테스트가 왜 문제를 발견하지 못했는지 단정할 수는 없다. 테스트의 구체적인 assertion, 모킹 환경, 실행 여부 등을 함께 확인해야 정확한 원인을 알 수 있다.

그래도 한 가지는 분명했다.

**테스트 케이스가 존재한다는 사실과 실제 사용자 환경에서 요구사항이 충족된다는 사실은 같지 않다.**

## 그런데 이 수정사항들은 애초에 TDD의 대상이었을까?

여기서 생각이 달라졌다.

내가 발견한 문제들을 모두 TDD로 해결하려고 했던 접근 자체가 적절했을까?

프론트엔드에서 검증해야 할 요구사항을 나눠보면 각각 적합한 방법이 다르다.


| 요구사항                 | 적합한 검증 방식       |
| -------------------- | --------------- |
| 조건 분기, 데이터 가공, 입력 검증 | 유닛 테스트          |
| 상태 변경, 모달, 버튼 동작     | 컴포넌트 테스트        |
| 실제 페이지 이동과 사용자 흐름    | E2E 테스트         |
| 색상, 여백, 이미지, 정렬      | 피그마 비교, 시각적 QA  |
| 화면 전체의 사용성과 완성도      | 직접 사용해 보는 개발 QA |


물론 TDD로 개발할 수 있는 기능과 그렇지 않은 기능을 명확히 이분법적으로 나눌 수는 없다. TDD는 다양한 수준의 테스트와 함께 사용할 수 있다.

하지만 **테스트할 수 있는 모든 것을 TDD로 개발해야 하는 것은 아니다.**

더구나 TDD와 테스트는 같은 개념이 아니다.

테스트는 구현 결과를 검증하는 수단이고, TDD는 테스트를 먼저 작성하면서 구현과 설계를 진행하는 개발 방법론이다.

나는 AI가 만든 결과물을 검증하고 싶었던 건데, 어느 순간 모든 기능을 TDD 절차에 맞춰 구현하는 데 집중하고 있었다.

## TDD는 원래 어떤 문제를 해결하려고 만들어졌을까?

이쯤에서 TDD의 목적을 다시 찾아봤다.

켄트 벡(Kent Beck)은 *Test-Driven Development: By Example*에서 TDD를 프로그래밍 과정의 두려움을 관리하는 방법으로 설명한다.

TDD의 핵심은 단순히 테스트 코드를 많이 만드는 데 있지 않다.

작은 단위로 실패하는 테스트를 작성하고, 이를 통과시키고, 리팩터링하면서 빠르게 피드백을 얻는다. 이를 통해 변경에 대한 불확실성을 줄이고, 작동하는 코드를 점진적으로 설계해 나간다.

즉, TDD는 **개발 과정에서 피드백을 얻고 설계를 개선하기 위한 방법론**이기도 하다.

반면 내가 해결하고 싶었던 문제는 조금 달랐다.

> AI가 PRD와 피그마에 정의된 요구사항을 빠짐없이 구현했는지 어떻게 확인할 것인가?

이 문제를 해결하는 데 TDD가 도움이 될 수는 있다. 하지만 TDD 하나로 모든 요구사항의 충족 여부를 보장할 수는 없다.

PRD에 있는 요구사항이 테스트 케이스로 옮겨지는 과정에서 빠질 수도 있고, 테스트의 검증 조건이 충분하지 않을 수도 있다. 테스트 환경과 실제 브라우저 환경이 다를 수도 있다.

무엇보다 시각적 구현처럼 다른 검증 방식이 더 직접적인 영역도 있다.

돌이켜보면 나는 **문제를 정확하게 정의하기 전에 해결책부터 선택했던 것** 같다.

## 그래서 TDD를 버리기로 했다

정확히 말하면 테스트를 버리는 것은 아니다.

**프론트엔드 개발 전체를 TDD 중심으로 진행하도록 설계한 워크플로우를 버리기로 했다.**

기존 방식은 PRD 작성부터 테스트 케이스 목록 생성, 테스트 작성, 최소 구현, 리팩터링, E2E 검증까지 단계가 많았다.

실제로 진행하면서 토큰 사용량도 많았고, 개발 시간도 길어졌다. 그런데도 요구사항 누락을 막지는 못했다.

물론 TDD를 적용하지 않았을 때와 동일한 조건으로 비교한 실험은 아니므로 TDD가 일반적으로 비효율적이라고 결론 내릴 수는 없다.

다만 적어도 **현재 내 목표와 작업 방식에는 절차가 과도하다고 판단했다.**

앞으로는 다음과 같은 흐름을 시도해 보려고 한다.

1. **PRD 검토:** AI와 함께 요구사항의 누락, 모호한 부분, 정상·오류·예외 상황을 먼저 확인한다.
2. **기능 구현:** UI와 사용자 동작을 구현하고, API 명세가 확정되면 연동한다.
3. **코드 리뷰:** AI와 사람이 함께 요구사항 충족 여부, 오류 처리, 유지보수성을 검토한다.
4. **개발 QA:** 실제 브라우저에서 기능을 조작하고 피그마와 비교한다.
5. **선택적 자동화 테스트:** 복잡한 비즈니스 로직이나 회귀 위험이 높은 기능에 필요한 테스트를 작성한다.

필요하다면 서로 다른 AI 모델을 활용한 교차 리뷰나 코드 리뷰 스킬도 시도해 볼 생각이다.

AI가 정상적으로 동작하는 코드를 만들어 주더라도, 그 코드가 항상 읽기 쉽고 유지보수하기 좋은 것은 아니기 때문이다. 코드 품질을 위한 규칙을 어디까지 정의할지도 계속 고민할 문제다.

아직 이 새로운 워크플로우가 더 효과적이라고 검증한 것은 아니다. 앞으로 직접 적용하면서 개선해 나가려고 한다.

## 방법론을 선택하기 전에 문제부터 정의하자

이번 경험을 통해 얻은 가장 큰 교훈은 **기술이나 방법론을 적용하기 전에, 그것이 왜 만들어졌고 어떤 문제를 해결하려는 것인지 이해해야 한다**는 것이다.

TDD가 좋은 방법론이라는 사실과 내 문제에 가장 적합한 해결책이라는 것은 다르다.

먼저 내가 해결하려는 문제를 명확하게 정의하고, 그 문제에 맞는 방법을 선택해야 한다.

AI가 작성한 코드를 신뢰하고 싶다면 테스트를 무조건 많이 작성하는 것보다 어떤 위험을 검증해야 하는지, 각 요구사항에 어떤 검증 방법이 적합한지 판단하는 일이 먼저일 수 있다.

그리고 테스트가 통과했다고 해서 검증이 끝난 것은 아니다.

특히 프론트엔드에서는 실제 화면을 보고, 클릭하고, 이동하면서 확인하는 과정도 여전히 중요하다.

## 그래도 일단 해봐서 다행이다

돌아보면 시간과 토큰을 꽤 썼다.

처음부터 TDD의 목적을 제대로 이해하고 적용 범위를 고민했다면 불필요한 시행착오를 줄일 수 있었을지도 모른다.

그런데 후회하지는 않는다.

나는 스스로 게으른 완벽주의자라고 생각한다. 무언가를 시작하기 전에 가장 좋은 방법을 찾으려고 한참 조사하다가, 정작 시작은 늦어지는 편이다.

이번에는 일단 해봤다.

그리고 직접 해보니 내가 무엇을 모르고 있었는지, 어떤 질문을 해야 하는지 알게 됐다.

TDD가 무엇인지 책으로 읽기만 했다면 이런 고민을 하지는 못했을 것 같다. 실제로 적용하고 불편함을 겪었기 때문에 내 문제를 다시 정의할 수 있었다.

이번에 찾은 방법이 정답인지는 아직 모른다. 아마 앞으로도 몇 번은 더 바뀔 것이다.

그래도 이제는 새로운 도구나 방법론을 접할 때 먼저 질문하려고 한다.

**“이 방법은 어떤 문제를 해결하기 위해 만들어졌고, 지금 내가 해결하려는 문제와 일치하는가?”**

AI 개발 워크플로우를 찾아가는 과정은 아직 진행 중이다.

일단 저질러 본 덕분에 다음 실험은 조금 더 잘할 수 있을 것 같다.
